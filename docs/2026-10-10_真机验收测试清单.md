### 1.2 优先级与结果定义

| 标识 | 含义 | 验收要求 |
|---|---|---|
| P0 | 核心正确性、状态真实性、无重复执行和无非法地址写入 | 声明支持的目标环境必须通过 |
| P1 | 兼容性、工具联动、恢复及长时间稳定性 | 交付所包含的能力必须通过；未通过要明确缩小交付范围 |
| P2 | 故障注入和极端边界 | 保存宿主验证，并争取完成 Android 定向验证；不能将未执行记成通过 |
| PASS | 步骤执行完，断言满足，证据齐全 | 可以计入通过数量 |
| FAIL | 行为或证据违反断言 | 建立缺陷并复测 |
| BLOCKED | 环境、夹具、权限或测量条件不足 | 写清缺少什么；不能计入通过 |
| NOT_RUN | 尚未执行 | 保持未执行状态 |
| N/A | 对该环境确实不适用 | 例如 ARM64 专属回调在 x86_64 不适用；必须写理由 |

“无法复现”“没看到事件”“工具返回成功”都不能单独作为 PASS。

## 2. 执行前准备

### 2.1 环境矩阵

| 环境编号 | 配置 | 必测范围 |
|---|---|---|
| A | 主要交付 ARM64 真机，记录 Android/ROM、KernelSU、ZygiskNext、LSPosed 版本 | 全部适用用例；ShadowHook fini/init 必测 |
| B | 第二套拟支持的 ARM64 Android/ROM 环境 | ENV、NAT、FP、LDR、JNI、JAV、关键 UI/异步及至少 1 小时稳定性 |
| C | 原生执行 x86_64 代码的 Android 环境，具备可工作的注入栈 | Dobby、Bionic dlclose、x86_64 栈参数及核心链路 |
| D | Windows/Linux/macOS PC，分别连接已验证设备 | MCP 启动、adb 路径、SDK 启动、报告及设备采集 |

环境 A 可先做完整验收。没有 B/C 时，结论只能覆盖 A；不能从 Linux CPU 测试推出 Android x86_64 已验证。
使用 ARM 翻译执行目标库的模拟器不能替代 C。C 也不能替代 ARM64 真机。
不在本文预先声明全部 Android 版本或全部 root 框架兼容。

### 2.3 测试应用和夹具要求

**仓库目前有宿主 C++/Python/Kotlin 测试，但没有一份现成 APK 覆盖下列所有场景。**
UI/报告等可先用已有可控测试应用执行；精确 ABI、卸载、ClassLoader 和故障注入用例需要准备专用夹具。
缺少夹具时将相应用例记为 BLOCKED，不用随机业务应用猜测原型或触发结果。

以下是建议的夹具接口契约，不表示这些类、符号或按钮已经存在：

| 部分 | 必须能控制和观察的内容 |
|---|---|
| 应用身份 | 建议包名 `com.example.reconbridge.fixture`，支持主进程与独立子进程；所有操作只修改本地测试数据 |
| Native 普通函数 | `librb_fixture.so` 导出 `int64_t rb_add(int64_t a, int64_t b)`，结果为 a+b；函数禁止内联 |
| Native 浮点 | `double rb_mix(int64_t a, float b, double c)`，结果为 a+b+c；另有 8 整数参数、8 浮点参数、void、位模式回显函数 |
| Native 并发 | 阻塞函数有 entered/release/completed 屏障，能够保持 5 秒以上在途；不是依靠随机 sleep 判断进入时刻 |
| Native 异常 | 测试函数抛 C++ 异常，由夹具调用者捕获；记录异常与析构计数，不让异常跨 JNI 边界逃逸 |
| 代码恢复证据 | 夹具在安装前/安装后/撤钩后复制目标入口至少 64 字节并计算哈希；同时记录实际调用结果 |
| 槽位 | 至少 65 个真实不同地址、相同已知 ABI 的函数，用于容量边界和连续复用 |
| 动态库 | 独立可卸载库、依赖库、两个不同目录的同 basename 库；记录每次 dlopen/dlclose、有效句柄引用数、基址、构造/析构计数 |
| JNI | 可重复注册、替换、注销的类；两个 ClassLoader 加载同名类；普通 Java_* 短/长名称导出库 |
| Java/异步 | 明确重载、返回值、异常方法；JobQueue.submit(Job) 与 Job.run() 使用同一对象；支持入队失败、同步执行、延迟执行和重复提交 |
| UI | 唯一 resource-id 按钮、重名节点、禁用节点、可聚焦文本框、密码框、页面切换、点击计数 |
| 动作学习 | 两种输入的本地业务方法、输入相关完成回调、可持久化执行次数；可生成同版本不同哈希 APK |
| 性能 | 无 Hook 基线、调用总数、错误数、P50/P95/P99、CPU、RSS/PSS、FD、线程、映射数量 |

普通卸载测试只关闭有效句柄，并保证应用不再使用已卸载函数。不要向 Android loader 传随机地址模拟失败。
“函数尚在运行时卸载代码”和“线程停在入口计数前”放到 DBG 专用实验，不作为正常业务流。
同地址重载必须记录实际基址；地址没有重用就不能将“同地址场景”记为通过，也不要用覆盖映射强行制造普通验收结果。

每个用例保存以下文件，允许一个 JSON 合并请求和响应，但不能只保留截图：

    runtime-after.json

`environment.md` 记录设备/ABI/ROM、root 与注入框架版本、PC 系统、adb/Java/Python/SDK 版本、代码提交和三个安装包 SHA-256。
用例记录 package、PID、process_instance、daemon stream_id、开始/结束时间、输入、期望/实际结果、执行次数、错误和证据路径。
崩溃或 ANR 时另存可取得的 tombstone/ANR/bugreport、相关线程栈；权限不够时明确记录不可取得。

Windows PowerShell 采集示例：在**准备实际测试时**从仓库根目录执行。交互输入真实测试设备序列号；本段不会自动安装或清理设备。

```powershell
$testSerial = Read-Host '输入测试设备序列号'
$testOut = Join-Path (Get-Location) ('dist/device-acceptance-' + (Get-Date -Format 'yyyyMMdd-HHmmss'))
New-Item -ItemType Directory -Path $testOut -Force | Out-Null
$env:RECONBRIDGE_SERIAL = $testSerial
adb -s $testSerial shell getprop ro.build.fingerprint | Out-File (Join-Path $testOut 'fingerprint.txt') -Encoding utf8
adb -s $testSerial shell getprop ro.product.cpu.abilist | Out-File (Join-Path $testOut 'abi.txt') -Encoding utf8
adb -s $testSerial shell getconf PAGESIZE | Out-File (Join-Path $testOut 'page-size.txt') -Encoding utf8
Get-FileHash -Algorithm SHA256 -LiteralPath 'dist/ReconBridge-native-lifetime.zip','dist/ReconBridge-PC-native-lifetime-win64.zip','dist/ReconBridge-Tracer-1.2.0-debug.apk' |
    Format-List | Out-File (Join-Path $testOut 'artifacts-sha256.txt') -Encoding utf8
adb -s $testSerial logcat -d -v threadtime | Out-File (Join-Path $testOut 'logcat.txt') -Encoding utf8
```

如果 MCP 由桌面客户端启动，serial 必须设置在该客户端的 MCP 环境配置里并重启 MCP；当前终端的环境变量不会改变已经运行的 MCP 进程。
截图使用 `capture_ui` 保存，避免通过文本重定向破坏 PNG。原始 XML、截图、trace 和 logcat 按本地测试证据保管；报告脱敏并不代表这些原始文件已脱敏。

通用规则：

1. 每项先保存配置、runtime 和事件起始游标；需要采集触发过程时，先开启窗口，再在另一端操作夹具。
2. 普通安装、重配置和空闲撤钩每 250 ms 查询一次状态，建议先给 5 秒观测窗口；这是测试超时参数，不是产品 SLA。超时保存状态并调查，不把无响应记为成功。
3. `pending` 的未加载库没有固定 30 秒失败承诺；已加载但符号未解析约 200 次维护后失败，维护间隔 150 ms，使用至少 40 秒观测窗口并记录调度延迟。
4. 每项结束清理本项 Hook；保留资源的用例先保存证据，再重启专用测试进程恢复。一个用例残留的槽位不得污染下一项容量测试。
5. `hot_injected/hot_unhooked` 是投递连接数；物理撤钩用状态、代码字节及实际返回值共同判断。
6. 无法观察瞬时状态时使用屏障或定向夹具，不能要求所有短暂状态都被普通轮询命中。

## 3. 环境与基础连接

### ENV-01｜P0｜部署版本与能力一致

**步骤：**记录安装包哈希并完成安装重启；启用测试包作用域；调用 `device_status()`、`diagnose_target(package)`；配置一个 Native 点和 JNI 观察后启动测试应用，再查询 `runtime_hook_status(package)`。

**通过标准：**第 2.2 节版本符合；Native/Java 连接按 kind 区分；期望配置与实际安装分别显示。若版本不符，后续验收 BLOCKED，不能以磁盘上有新文件代替进程已加载新版。

**证据：**环境记录、health、完整诊断和 runtime JSON。

### ENV-02｜P0｜冷启动、目标作用域与多进程

**步骤：**先配 Hook 再启动测试包；分别触发主进程和子进程函数；对照未纳入测试配置的第二包；重启目标再触发。

**通过标准：**命中属于正确 package/PID/process_instance；重启后使用新实例；第二包不被误改。Java 与 Native 两条连接不能误当成两个业务进程。

**证据：**三组调用返回值、进程列表、事件与重启前后状态。

### ENV-03｜P1｜adb、Wi-Fi 与多设备选择

**步骤：**先用 adb transport 验证；在已配置 Wi-Fi transport 时复测 HTTP 操作；保持 HTTP 正常但让测试 adb 不可用，调用 UI/Perfetto；另测唯一在线设备加 offline 残链、两台在线设备和显式 serial。

**通过标准：**唯一在线设备可被识别；多台在线且未指定时明确报错；显式 serial 的操作只落到所选设备。Wi-Fi HTTP 正常不能掩盖 UI/Perfetto 缺少 adb 的错误。

**证据：**脱敏连接配置、选中 serial、设备侧操作计数和各错误响应。

### ENV-04｜P1｜手机 MCP 与 PC MCP 入口

**步骤：**PC 枚举工具并检查 103 个；手机启用本地 MCP，以配置的认证头连接并检查 49 个；分别执行状态查询和已有 JNI 查询；缺失/错误认证头时尝试手机 MCP 请求。

**通过标准：**正确配置可连接；错误认证被拒绝；手机侧不存在的 PC 高层能力不被宣称可调用；响应能够明确区分连接失败与空结果。保存记录时隐藏真实 token。

**证据：**工具清单、脱敏请求/响应。

## 4. Native 撤钩与槽位

下面 JSON 是 **`post_hook` 的参数对象**，适用于按第 2.3 节实现了夹具后的测试，不是独立 shell 命令。

```json
{
  "config": {
    "package": "com.example.reconbridge.fixture",
    "mode": "append",
    "restart": false,
    "targets": [{
      "id": "accept_add",
      "kind": "native",
      "lib": "librb_fixture.so",
      "symbol": "rb_add",
      "signature": {"args": ["int64", "int64"], "ret": "int64"},
      "capture": {
        "args": [{"index": 0, "type": "int"}, {"index": 1, "type": "int"}],
        "ret": {"capture": true, "type": "int"}
      },
      "action": {"type": "replace_ret", "ret_value": 99}
    }]
  }
}
```

### NAT-01｜P0｜新增、替换与真实命中

**步骤：**无 Hook 调用 rb_add(3,7) 得到 10；安装示例配置并等 installed，调用应得 99；同 ID 更新替换值为 123，再调用；移除前保存事件和状态。

**通过标准：**PID 不变，最终返回随配置改变；事件关联正确 ID/代次与 `native_config_revision`。返回采集记录原函数的 10，应用收到替换后的 99/123；不能要求事件 ret 自动变成替换值。

**证据：**请求、版本号、三次业务结果、对应事件。

### NAT-02｜P0｜空闲时物理撤钩

**步骤：**夹具保存未安装时入口 64 字节；安装后再保存并确认替换生效；调用 `unhook(package, "accept_add")`；等待 removed 且 `slots_used` 回到用例前值；再次保存入口并调用 rb_add。

**通过标准：**撤钩后入口与安装前逐字节相同，业务恢复 10；新调用不再产生本 Hook 的采集事件；未重启目标。只看到返回正常或 removed，而没有字节证据，不能算“物理恢复已验证”。

**证据：**三份字节/哈希、retained_hooks、slots_used、撤钩后独立事件窗口。

### NAT-03｜P0｜在途调用结束后撤钩

**步骤：**线程进入带屏障的阻塞函数并确认 entered；保持至少 5 秒，执行 unhook；查询 draining 与 in_flight；释放屏障并等调用返回，观察 removed 和槽位回收；再调用一次。

**通过标准：**在途时不恢复入口、不回收槽位；旧调用按进入时的配置完成；后续调用恢复原行为。允许旧调用在 unhook 投递后才发事件，但其 revision 必须属于旧配置；无死锁、错误返回和崩溃。

**证据：**屏障时间线、状态序列、入口字节、旧/新调用的返回和 revision。

### NAT-04｜P0｜同进程连续复用超过 64 个点

**步骤：**每次安装一个不同真实地址，调用、撤钩、确认回收，再换下一个；至少 130 次，建议 2,000 次；全程不重启进程。另挑一轮在已回收槽位上换成浮点目标。

**通过标准：**第 65 个及之后仍可安装；slots_used 随回收降低；新目标的 ABI、原函数和行为不串到旧目标。入口保护记录可以增加，但仍有上限；这不等于引擎全部内存已释放。

**证据：**每轮目标地址、slot/generation、guard 数、返回值、PID、内存曲线。

### NAT-05｜P0｜64 槽容量边界与恢复

**步骤：**干净进程中安装 64 个不同地址；申请第 65 个；确认原 64 个仍生效；删除至少一个并等回收，再安装新点。另测满额时整批更换 64 个点。

**通过标准：**不足时明确拒绝，保留旧配置，不出现半批配置切换；先删除、等回收后可以新增。满额直接换点无需被视为必然成功；draining/撤钩失败的槽位仍计入占用。

**证据：**configuration 错误、retained_previous_config、前后 revision、全部 64 个点的结果。

### NAT-06｜P0｜无效配置与别名冲突

**步骤：**在有效 Hook 工作时依次提交重复 ID、重复点、超过 8 参数、variadic、不支持类型和保留点签名变更；另用符号/offset 两种选择器指向同一地址。

**通过标准：**无效配置不替换原有效配置；不能改变保留点的 ABI。地址别名不能拥有两份互相覆盖的机器码补丁；以拒绝/明确安装失败收敛。先删除并确认回收后，才允许对真实匹配的新目标重新声明 ABI。

**证据：**各请求与错误、旧点持续正确的调用结果。

## 5. 浮点与调用约定

### FP-01｜P0｜整数、指针与浮点混合参数

**步骤：**声明 rb_mix 的完整签名 `[int64,float,double] -> double`；调用 (2,1.5,3.25)，基线为 6.75；替换参数 b 为 1.25，结果应为 6.5；单独改为替换返回值 2.5。

**通过标准：**参数按逻辑下标对应，不因 GP/FP 寄存器分离错位；参数采集为传入原函数的替换后值，返回采集为替换前原结果。另用真实有效指针参数验证混排，不用任意地址充当 ptr。

**证据：**完整 C 原型、请求、应用实际值和事件 value/bits。

### FP-02｜P0｜8 参数和 x86_64 栈传参

**步骤：**分别测试 8 个浮点参数、8 个 int64 参数和混合 8 参数；给每个参数不同值，用带权校验函数识别位置；x86_64 单独替换第 7/8 个整数参数；重复启用/撤钩。

**通过标准：**所有参数位置和返回值匹配无 Hook 参考；栈参数正确；相邻调用的寄存器、栈和返回地址不受破坏。不能只用求和验证参数顺序。

**证据：**原型、输入向量、无 Hook/Hook/撤钩结果、至少 1,000 次循环统计。

### FP-03｜P1｜NaN、Inf、负零与舍入

**步骤：**夹具按原始位模式构造 +0、-0、±Inf、NaN payload、小数和次正规数，通过不做额外运算的回显函数采集；解析事件 JSON；另提交 NaN/Inf 或超出 float 范围的替换配置。

**通过标准：**JSON 合法；特殊值使用 null/special，bits 保留位模式，负零可区分；非法替换被拒绝。若平台对次正规数或算术 NaN 有变化，先以无 Hook 同路径结果定位，不把算术变化误判为序列化错误。

**证据：**输入/输出 bits、JSON 解析结果、无 Hook 对照和拒绝响应。

### FP-04｜P0｜void、C++ 异常与透传

**步骤：**测试 void 函数副作用和禁止采集/替换 void 返回；让被 Hook 函数抛异常并由夹具调用者捕获；检查析构/清理计数，再撤钩；禁用浮点 Hook 后继续调用。

**通过标准：**异常能跨生产网关展开，RAII 在途计数释放，不永久 draining；副作用只执行一次；禁用后参数和返回按原签名透传。异常不得逃出 JNI 接口进入 ART。

**证据：**异常类型、析构计数、撤钩状态、后续正常调用结果。

## 6. 库加载、卸载与重载

### LDR-01｜P0｜未加载库和无效符号

**步骤：**对尚未加载库配置 Hook，等 40 秒后再加载并调用；另对已加载库配置不存在的符号，观察至少 40 秒；分别记录状态。

**通过标准：**未加载库保持 pending，加载后维护线程安装；已加载但连续约 200 次无法解析符号后报告 failed。构造函数和首次维护前调用允许漏采，不能写成已保证覆盖。

**证据：**加载时间、installed 时间、维护尝试数、构造期与安装后调用分开的计数。

### LDR-02｜P0｜真实卸载与仅减引用

**步骤：**加载同一库两次，配置并触发 Hook；关闭一个有效句柄，确认库仍在；关闭最后一个且夹具不再使用其地址；对照 loader 事件、析构计数和实际映射。

**通过标准：**仅减引用不报告已卸载；真正离开后报告 native_library_unloaded。ARM64 的 native_library_unloading 只代表进入 fini，不能提前宣称 unmap；x86_64 不要求产生 ARM64 的同一中间事件。

**证据：**有效引用变化、前后映射、完整路径/基址/generation、loader_seq 与 observation_order。

### LDR-03｜P0｜卸载后重载和路径歧义

**步骤：**保留期望配置，安全卸载/重载同一库 100 次，记录每次基址；观察新的 generation 和重新安装；另同时加载不同目录但相同 basename 的两份库。

**通过标准：**新代次独立，旧记录不复活；重载后调用正确。同址重载只在实际发生时判定该子场景；不同路径同名同时可见时拒绝猜测安装位置，不能 Hook 错库。

**证据：**每轮路径、基址、generation、Hook 状态和返回值；同址发生次数。

### LDR-04｜P0｜依赖库、析构内关闭和存活库重装

**步骤：**加载带依赖库的夹具，在两个库设 Hook；析构函数按已知顺序关闭另一个有效句柄；执行外层关闭并核对依赖实际存活情况；x86_64 另做只减引用的 close 后持续调用存活库。

**通过标准：**观察实际消失的依赖，不漏掉嵌套 dlclose；不死锁；close 返回值和 errno 相对无 Hook 对照保持语义。x86_64 存活库应恢复安装并复用其入口记录，短暂漏采作为已知窗口计量，不宣称零丢失。

**证据：**析构顺序、close 返回/errno、存活库重装耗时、guard 数和事件缺口。

### LDR-05｜P1｜观察能力缺失与边界标识

**步骤：**在回调/符号不可用的兼容性环境，或专用测试构建中模拟注册失败；查询 runtime 和 diagnose_target；用轮询仍能观察的长时间卸载场景复测。

**通过标准：**loader 为 partial/unavailable，continuous 如实反映能力；诊断有提示，不能把快照轮询称为完整连续观察。raw munmap、自定义 loader、x86_64 非 dlclose 路径不因此被声明覆盖。

**证据：**失败 API/错误码、能力 JSON、诊断和实际事件。缺少该环境/注入点时记 BLOCKED。

## 7. JNI 映射

### JNI-01｜P0｜观察器安装与成功注册

**步骤：**调用 configure_jni_capture(package)，重启并打开夹具；检查两个 observer 安装项；成功注册已知方法，调用方法并查询 inspect_jni_bindings；对比未开启时已发生的历史注册。

**通过标准：**类、方法、签名、函数地址、模块/偏移正确；返回结果不改变；只记录实际观察到的注册，不补造历史；两项均成功才称 installed，单项成功报告 partial。

**证据：**观察器状态、原生注册返回、Java 调用返回、bindings 与 maps。

### JNI-02｜P0｜重注册与注销

**步骤：**同一类同一签名先注册函数 A，再合法替换为 B，分别调用；执行 UnregisterNatives；查询包含历史和 include_inactive=False 两种视图。

**通过标准：**旧映射 superseded、新映射 observed_registered；成功注销后为 unregistered；活跃过滤不返回旧记录。原注册/注销的结果和 VM 异常语义不被观察器改变。

**证据：**A/B 返回值、原 JNI 返回码、状态序列。失败返回及待处理异常的定向分支见 DBG-03。

### JNI-03｜P0｜同名类与进程身份隔离

**步骤：**两个 ClassLoader 加载同名类并分别注册；只注销其中一个；子进程注册同名方法；重启主进程重新注册。

**通过标准：**class_id、连接和 process_instance 能区分身份；只改变目标类记录；PID 重用/重新连接不能与旧绑定合并。不能只按类名或裸 jclass 地址归并。

**证据：**ClassLoader 夹具身份、class_id、connection/instance 和完整历史。

### JNI-04｜P1｜类回收与缓存边界

**步骤：**释放自定义 ClassLoader/类的强引用并请求 GC；用夹具弱引用确认实际已回收，再触发一次 JNI 观察；持续创建并释放类，另检查活类容量和映射历史淘汰。

**通过标准：**后续观察可标记 class_collected；观察器不因强引用阻止回收。未实际回收不能要求立刻变状态；超过 1024 活类身份或 4096 映射缓存时按不确定/淘汰语义报告，不错误复用身份。

**证据：**弱引用状态、观察时间、identity_unknown、mapping_cache.evicted_total 和内存趋势。

### JNI-05｜P0｜库卸载导致映射失效

**步骤：**用可控 dlopen 库里的函数进行 JNI 注册，停止使用这些方法后安全关闭库；观察映射状态；重载后重新注册；查询活跃过滤和地址检查。

**通过标准：**路径/可执行区间和观察顺序吻合的旧记录转为 module_unloading/module_unloaded；新注册不被旧代次覆盖。maps 显示 mapped 仍不等于 VM 绑定有效，`current_bindings_verified` 始终 false。

**证据：**registration 与 loader 的 observation_order、路径/地址、前后 bindings。普通随机调度不能替代 DBG-03 的确定性乱序验证。

### JNI-06｜P1｜Java_* 静态导出与地址解释

**步骤：**对设备上的独立 ELF 文件执行 inspect_jni_exports；检查短名、长名重载、下划线/数组/Unicode 名称；对无效 ELF、32 位库和 APK 内路径请求；普通导出地址与运行时 load bias 对照。

**通过标准：**返回 export_candidate；不推测返回类型和完整 signature，不称为已绑定。elf_value 是相对加载偏置的虚拟地址，不是文件偏移；IFUNC 若存在标为 resolver，不能按普通函数直接验算最终入口。超范围输入明确报错。

**证据：**ELF 哈希、导出符号表、工具输出与地址对照表。

## 10. 异步关联

### ASY-01｜P0｜同一任务对象跨线程匹配

### ASY-04｜P0｜进程重启与 namespace 隔离

**通过标准：**不同 instance/namespace 不跨接；旧事件不连接新任务；缺少成功入队证据时保持 unresolved；complete 不被误设为整个应用路径已完整。

**证据：**混合事件输入、期望边列表、实际关联结果。

## 11. 事件完整性与断线

**证据：**发送/接收计数、完整性字段、停止原因、已保留文件。

### EVT-03｜P0｜daemon 重启和 Runtime 通道断开

**步骤：**采集中通过受控管理操作重启 daemon；保持目标应用运行，查询旧窗口和 JNI 历史；尝试下发新配置；保存证据后重启测试应用建立新连接。

**通过标准：**stream_id 改变、旧游标 cursor_reset；窗口不能续称完整；旧 JNI 记录 runtime_disconnected 不等于已确认进程退出。Native 当前连接不自动重连，保留最后行为；新配置不能被误报已经在旧进程生效，重启后才验证新连接。

**证据：**daemon/进程存活记录、旧新 stream/instance、配置投递和实际调用结果。

## 12. 动作学习与运行保护

仅使用夹具本地业务计数，不将测试指向付款、发布或其他真实外部业务动作。
详细参数示例见 [ACTION_LEARNING.md](../pc/ACTION_LEARNING.md)。

### ACT-01｜P0｜示范、参数绑定、预览和一次执行

**步骤：**拉齐目标 base/split APK；用两种 item_id 分别 begin/finish_action_capture；比较示范，创建精确签名计划并绑定动态输入；默认 dry_run 预览；再执行一次，成功条件关联当前 item_id。

**通过标准：**预览不增加业务次数；实际只执行一次；返回 Ack 不等于成功，必须满足指定结果和当前输入身份。截断示范、缺失参数或仅有对象 toString 的记录不能冒充可执行实参。

**证据：**两份 capture、计划、参数解析、业务计数、结果检查和执行回执。

### ACT-02｜P0｜防重复、次数/间隔与不确定执行

**步骤：**同 dedup_key 重复提交；达到 max_runs 和 min_interval_ms 边界；重启应用后再次尝试重复键；制造动作已开始但 RPC 超时/验证未完成；再尝试新提交。

**通过标准：**设备持久化预留阻止重复；重启不清零历史；失败/未确认后停止自动后续提交，不自动重试。已进入 Java 方法无法被超时强制撤销，回执保持不确定；不以 disable/uninstall/rollback 清除业务保护记录。

**证据：**持久化状态、run_id/dedup_key、真实业务次数及跨重启时间线。

### ACT-03｜P0｜计划兼容性、安装和包权限

**步骤：**验证同一精确计划成功后安装并用 use_installed 执行；修改计划后尝试直接安装；升级夹具或换同版本不同 SHA-256 APK、缺失一个 split 后检查兼容性；对导出包篡改内容/目标包/签名再验证导入。

**通过标准：**只有已验证的精确计划可安装；APK/版本/split 改变阻止沿用；哈希、签名、allowed_packages 与权限检查按策略生效。allow_untrusted 不得绕过签名和内容校验；不把签名包导出称为独立 LSPosed APK。

**证据：**前后 APK 清单、计划摘要、manifest、拒绝原因与执行记录。

**证据：**合成目录统计、跳过清单、ZIP 内容与哈希。

## 14. Android 工具与静态分析

### SDK-01｜P1｜真实 apkanalyzer 与跨平台路径

**步骤：**在实际 PC 分别运行 summary/manifest/permissions/files；用本次 Tracer APK 和测试 APK 对照；覆盖带空格/中文路径、SDK 显式路径、缺失工具及损坏 APK。

**通过标准：**存在工具时与独立 SDK 命令输出一致；启动参数正确；缺失/损坏返回可诊断错误；输出限额明确为尾部而非完整文档。Windows/Linux/macOS 各记录实际执行环境，不能用单平台结果覆盖全部。

**证据：**工具路径版本、APK 哈希、四项输出和失败响应。

### SDK-02｜P1｜Perfetto 采集和远端清理

**步骤：**capture_perfetto(session_id, seconds=10, buffer_mb=8) 期间操作夹具；在本地解析器打开 trace，确认是否有预期数据源；再测 1 秒/60 秒边界、非法参数、设备命令缺失或权限失败。

**通过标准：**成功时文件非空、可解析；数据源不足明确记录，不能仅凭文件存在认定调度信息齐全；scope 为系统级而非仅目标包；只清理本次临时文件，不删除其他 trace；decoded=false，不宣称已计算性能指标。

**证据：**trace 哈希、解析摘要、操作时间线、失败响应与临时文件检查。

### SDK-03｜P1｜拉包、索引与静态到运行时链路

**步骤：**open_target 自动拉取可控应用完整 APK 集合；prepare_index、search_target、inspect_method 定位夹具已知方法；执行一次 trace_target 验证；源码版 PC 与冻结版分别重复核心路径。

**通过标准：**base/split 不遗漏；索引和源码对应本次 APK；静态候选与实际命中分开标记；缺失 jadx/其他外部工具时返回明确缺项而非伪造分析成功；会话证据可导出复查。

**证据：**APK 清单/哈希、定位结果、源码、命中事件、工具缺失错误。

## 15. 并发、稳定性与恢复

### STB-01｜P0｜多线程调用与配置并发更新

**步骤：**夹具用至少 8 个线程持续调用整数/浮点函数；另两个控制任务交错 append、行为替换和 unhook，持续 10 分钟；每轮先确认容量条件，记录所有 revision；函数内部另含合法 dlopen/dlclose 路径。

**通过标准：**单次调用只使用进入时的一份配置，不出现半旧半新参数或跨目标返回；无死锁、栈损坏、native 崩溃；并发 append 不丢已接受的配置。撤钩后的旧调用按旧 revision 完成是允许行为。

**证据：**控制操作日志、逐调用期望值校验、线程栈、错误计数和 revision 分布。

### STB-02｜P1｜长时间运行与资源趋势

**步骤：**同一环境先做无 Hook 基线，再做纯观测、行为替换、持续 UI/异步采集三种负载；冒烟 30 分钟、主验收 8 小时，长期使用目标建议再做 24 小时。每分钟记录 RSS/PSS、CPU、FD、线程、映射、槽位、guard、缓存/丢弃计数和调用延迟。

**通过标准：**零非预期崩溃/ANR/重复业务副作用；资源随已知保留对象增长的部分能解释，达到缓存上限后不得继续因同一缓存无界增长。性能与内存必须对照本批次预先记录的预算；未设预算只能形成测量报告，不能签署性能达标。

**证据：**基线和各负载 CSV、P50/P95/P99、8/24 小时日志及异常现场。入口页按实际页大小计量，不假设所有设备是 4 KiB。

### STB-03｜P1｜入口上限和 x86_64 引擎内存保留

**步骤：**专用进程连续安装/撤钩直至 4096 个独立入口，再请求新入口；另在 x86_64 同一组存活库上循环有效 dlclose/重装至少 1,000 次；比较 guard 数与总 RSS/PSS。

**通过标准：**到达 guard 上限明确要求重启，不能越界分配或串用旧上下文；存活库重装复用已有入口。Dobby 内部记录/重定位内存可能继续保留，单独报告增量和可用运行时长；不能用“guard 数稳定”证明总内存稳定。超出既定内存预算仍算未通过长期使用验收。

**证据：**入口计数、引擎重装次数、内存斜率、上限响应和重启后恢复。

### STB-04｜P0｜清理、重启和新会话恢复

**步骤：**保存末次证据；按 Hook ID 清理用例配置；关闭 JNI 期望配置后退出/重启测试进程；重新打开干净会话并执行 NAT-01/02 和 JNI-01；检查临时文件及遗留连接。

**通过标准：**普通 Native/Java Hook 已清理；JNI observer 不能被误称为即时 live unhook，停止以进程退出为边界；旧进程退出后保护入口与进程内资源释放；新会话不会混入旧实例事件。清理失败必须记录，不能隐藏在完成提示中。

**证据：**清理回执、最终 list_hooks/runtime、旧新 PID/instance、恢复后冒烟结果。

## 16. 需要定向夹具的故障注入

此组不是通过破坏正式应用地址、随机关闭句柄或诱发系统崩溃来执行。测试构建与正式包分别记录哈希；测试构建结果不能冒充正式包完整兼容性结果。

### DBG-01｜P2｜引擎撤钩失败不回收槽位

**前提：**在测试构建的引擎调用封装层提供一次性失败注入，并记录真实调用次数。

**步骤：**安装 Hook 后让下一次 unhook API 返回失败；删除配置；观察多轮维护；尝试复用该槽位并检查原地址。

**通过标准：**状态为 unhook_failed，slot_reclaimable=false，资源保留；不重复调用可能已被 ShadowHook 消费的旧句柄；不伪报 removed，不将该槽位交给新目标。

**证据：**故障开关、引擎调用计数、槽位/状态、原地址字节和诊断输出。

### DBG-02｜P2｜计数前延迟入口与失效库上下文

**前提：**调试夹具可以在 RX 入口已经选定、尚未进入 C++ 在途计数的位置暂停单个线程，并保存其上下文；另用隔离测试构建控制 module_valid。

**步骤：**暂停旧入口线程；完成撤钩并把逻辑槽位分给不同签名目标；恢复线程；另执行旧上下文被标失效的分支。

**通过标准：**旧入口不读取新槽位签名/原函数，不跳入已释放跳板；正常撤钩后走原地址透传。已失效上下文不再跳旧地址，原始结果寄存器置零，但不能把它解释为业务成功。检查 RX 页没有因自身生成过程永久保留 RWX。

**证据：**暂停点 PC/线程、generation、分支轨迹、页权限和实际返回。应用卸载仍在执行的代码本身不受通用安全保证，不能据此承诺任意并发 dlclose 均无崩溃。

### DBG-03｜P2｜JNI 失败语义与卸载事件乱序

**前提：**可控制 JNI 封装返回/观察器自身异常，并可在进入 daemon 前延迟 loader 事件；不得靠非法 JNI 参数强迫 ART 崩溃。

**步骤：**分别模拟原 Register/Unregister 失败、原 VM 已有待处理异常、观察器自己产生异常；另在旧卸载边界 order=20 前注册 A(order=10)，边界后注册 B(order=30)，延迟送达 order=20 的卸载事件；再测其他连接的同地址记录。

**通过标准：**不把失败调用记为成功；原异常不被清除，只清理观察器引入的异常。旧卸载只影响 A，不影响 B 和其他连接；后续确认卸载沿用原卸载边界，不凭到达时间覆盖新注册。缺少排序信息时不强行推断。

**证据：**原 JNI 返回/异常、准确事件投递顺序、observation_order、连接身份和映射状态。宿主已有覆盖，可作为对照，不能替代未执行的 Android 故障注入记录。

## 17. 已知边界与验收判定

下列现象不能直接当成“还未实现”的缺陷，但必须如实体现；如果交付场景依赖这些能力，则该场景尚不能通过验收。

| 当前边界 | 测试时如何处理 |
|---|---|
| 64 个并发占用逻辑槽位；4096 个保留入口 | 验证回收、边界拒绝和状态，不要求无限安装 |
| 入口上下文及部分引擎内存留到进程退出 | 验证增长来源和业务预算，不要求每次 unhook 后 RSS 回到基线 |
| x86_64 dlclose 时可能短暂撤掉存活库 Hook | 记录漏采和恢复时间，不宣称全程无窗口 |
| 新库安装由维护线程完成 | 不保证构造函数及最早调用捕获 |
| raw munmap、自定义 loader、部分 TLS 延迟释放 | 不纳入完整连续卸载覆盖承诺 |
| Native ABI 仅普通标量、最多 8 参数 | 不测试成“应该支持”结构体/HFA/SIMD/可变参数/long double/自定义 ABI |
| JNI 是有界观察历史 | current_bindings_verified=false；不冒充全量当前 VM 绑定表 |
| Native/JNI 当前通道断开不自动重连；JNI 配置需重启 | 验证状态与恢复流程，不假定后台自动修好 |
| UI 层级和截图非原子；选择检查与输入有间隔 | 保留变化/不确定性，不将 assert 节点存在当业务成功 |
| 没有任意手势录制、swipe、WebView DOM 或自动 coroutine/Binder 传播 | 不列为本批实现缺陷；需要时另列功能需求 |
| Perfetto 保存原始系统 trace，未自动解码指标 | 验证 trace 和范围，指标由独立解析步骤提供 |
| 事件完整性只覆盖 daemon 已收到部分 | upstream_loss=unknown；没有丢弃计数不等于源头全量捕获 |

发布判断：

1. 每个声明支持的环境，适用 P0 全部 PASS；无未解释的崩溃、ANR、错误修改、重复执行或身份串线。
2. 交付范围内 P1 全部 PASS；否则列出受限环境/功能、缺陷与影响，不用一句“基本正常”覆盖。
3. P2 若未执行，明确标为 BLOCKED/NOT_RUN，列出已有宿主证据与尚缺的 Android 证据。
4. 稳定性达到所选运行时长，内存/性能有明确预算和对照结论；不能仅因设计允许保留内存就忽略实际不可用。
5. 留存完整原始证据、失败尝试、修复提交和复测结果；任何修复只重跑受影响项与必要冒烟，并记录范围。
